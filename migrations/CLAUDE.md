# migrations

Trusted, hand-written PostgreSQL DDL that `runMigrations` (`packages/postgres/src/migrations.ts`) applies in filename order. This folder owns the schema, the group roles, RLS policies, grants and the `unai_private` functions. It holds no LOGIN role or password (deployments and tests create logins and grant them `unai_app` or `unai_auth`) and no seed data; the only top-level `INSERT`s are backfills from existing tables (0005, 0008).

## How the runner treats a file

- Only `.sql` entries are read. One that does not match `^\d{4}_[a-z0-9_]+\.sql$`, or that repeats a four-digit prefix, fails the whole run with `MIGRATION_NAMES_INVALID` before any SQL executes.
- The ledger `unai_migrations.applied` must be an exact prefix of the sorted file list, by name and by SHA-256, or the run stops with `MIGRATION_HISTORY_MISMATCH`. Never edit, rename or delete an applied file, and never add one that sorts before an applied one: take the next free number. The digest covers the raw bytes and `.gitattributes` does not pin line endings for this folder, so a line-ending conversion alone changes it; the files are LF, keep them so.
- Each file is sent as one multi-statement query inside the runner's transaction, together with its ledger insert. Write no `BEGIN`, `COMMIT` or `ROLLBACK`, and nothing that cannot run in a transaction block (`CREATE INDEX CONCURRENTLY`, `VACUUM`). The outer `BEGIN;`/`COMMIT;` in `0001_foundation.sql` is a grandfathered envelope the runner strips. Nothing enforces this rule: an inner `COMMIT` would silently separate the DDL from its ledger row. The session runs with `statement_timeout='30s'`.
- A failure surfaces only as `MIGRATION_FAILED:<file>`; the PostgreSQL message is discarded on purpose. Run the file with `psql` against a throwaway database to see it. A failed file rolls back together with its ledger row, so a file that has never been applied anywhere can still be corrected.

## What an owner-scoped table migration contains

- `owner_scope_id uuid NOT NULL REFERENCES owner_scopes(id)`, plus `UNIQUE(owner_scope_id,id)` on any table that will be referenced. Children reference `(owner_scope_id, parent_id)` so a row cannot point across owners, and a member column is tied to its scope with `FOREIGN KEY(owner_scope_id,user_id) REFERENCES owner_scope_members` (`devices`, `auth_*`, `source_items.submitted_by_user_id`). Give a new text column a `CHECK` for length or a stable-code regex and a `jsonb` column a `jsonb_typeof` check, as nearly all existing columns have.
- The table lives in `public`; `assertOwnershipCoverage` rejects a table in any other schema.
- `ENABLE` and `FORCE ROW LEVEL SECURITY`, then one policy per command, `TO unai_app`: `FOR SELECT ... USING`, `FOR INSERT ... WITH CHECK` (only 0001 and 0002 use all-command `owner_isolation` policies). Each starts with `unai_private.has_owner_access(owner_scope_id)`. Per-user rows add `user_id=unai_private.actor_id()`; insert policies bind the writer column (`actor`, `submitted_by_user_id`) the same way. Purpose gates use `current_setting('unai.purpose',true)` or a helper such as `unai_private.job_purpose(ARRAY[...])`. Always pass `true` so a missing setting is NULL and the policy fails closed ("fails closed with no request context" in `isolation.test.ts`).
- Children of evidence add `EXISTS(SELECT 1 FROM source_items s WHERE s.owner_scope_id=<table>.owner_scope_id AND s.id=source_item_id)`. That subquery runs under the `source_items` policy, so purpose, sensitivity ceiling and `deleted_at` carry over and the child never widens the parent's decision.
- Grants are explicit and minimal. No migration grants `DELETE` or `TRUNCATE` to `unai_app`. Every owner-scoped table still needs `SELECT` on at least one column, or the CRT-SEC-01-A coverage test fails. Column-level grants hide secrets (`auth_sessions.token_hash`), which makes `SELECT *` on `auth_sessions` a `42501` for the application.
- Append-only tables get no `UPDATE` grant; `audit_events` and `evidence_ingestion_receipts` rely on that alone. The evidence tables (`source_items`, `source_anchors`, `evidence_object_keys`) add a `BEFORE UPDATE` trigger that raises `EVIDENCE_IMMUTABLE` with `ERRCODE='55000'`, and `jobs`, which is updatable, guards its identity columns the same way with `JOB_IDENTITY_IMMUTABLE` (the registry snapshot uses `42501`). Tests match on these SQLSTATEs. The trigger binds the migration owner too, so a later data fix must `DISABLE TRIGGER` and re-enable it in the same file, as 0008 does. Reuse `unai_private.immutable_evidence()` rather than writing another.
- A global table (0006) has forced RLS, no policy and `REVOKE ALL ... FROM PUBLIC, unai_app`.

Then do the TypeScript half described in `packages/postgres/CLAUDE.md`: the classification in `ownership.ts`, and the fixtures and table count in `isolation.test.ts`.

## Functions and roles

- Functions live in `unai_private` with `SET search_path=pg_catalog`, `public.`-qualified table names inside definer bodies and no dynamic SQL. After each `CREATE FUNCTION`, `REVOKE ALL ON FUNCTION ... FROM PUBLIC` and grant `EXECUTE` to exactly one role: `unai_app` for policy helpers, `unai_auth` for `auth_*`, nobody for trigger functions. The blanket `GRANT EXECUTE ON ALL FUNCTIONS` in 0001 covered only the functions that existed then.
- `SECURITY DEFINER` is reserved for functions that must read or write past RLS (`has_owner_access`, `auth_*`, the session-revocation triggers). Helpers that only read settings (`actor_id`, `owner_id`, `evidence_access`, `job_purpose`) are plain `STABLE`. Definer functions run as the privileged migration owner that bypasses forced RLS (`docs/foundation.md`; the restricted definer role of ADR 0009 was rejected and never implemented), so the body does its own owner and membership filtering and writes its own `audit_events` row, as `auth_create_session` does.
- The group roles are `NOLOGIN NOINHERIT`. For a new one, copy the `DO $$ ... IF NOT EXISTS (SELECT FROM pg_roles ...)` block and the unconditional `ALTER ROLE` line from 0001 or 0002.

## Traps

- Purpose lists are literals inside applied files (`evidence_access` in 0004, the `jobs` policies in 0007). A new purpose needs a new migration that replaces the function or drops and recreates the policy.
- Renaming or dropping a column breaks raw SQL elsewhere. `source_items` inserts live in `packages/api/src/evidence.ts` and in the fixtures of `packages/postgres/src/isolation.test.ts`, `packages/jobs/src/index.test.ts` and `packages/api/src/evidence.test.ts`. 0008 renamed `raw_object_id` to `raw_object_ref`, and `docs/evidence-runtime.md` notes which passages still describe the pre-0008 names.
- No test lives here. `pnpm test` applies this folder before vitest starts and names that step `MIGRATION_FAILED`. `packages/postgres/src/migrations.test.ts` tests the runner against temporary directories, not these files; the schema itself is asserted by `isolation.test.ts`, `auth.test.ts` and each database-backed package.
